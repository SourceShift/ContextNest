# Upgrading to v0.2.0 (disk-first substrate)

This guide is for operators who already run `contextnest serve` with
persistence on (a WAL at `~/.contextnest/wal.jsonl` and a canonical
checkpoint next to it at `wal.canonical.sqlite`). A fresh install needs none
of this.

## What changes, in one paragraph

v0.2.0 stores each embedding once instead of ~3.5 times, keeps the
connection graph as compact integer records, and writes vectors to the
checkpoint as binary blobs instead of JSON text. On a 330 k-fragment
substrate the server's live heap was 12.4 GB before the change; most of it
sat in macOS's compressor and swap, which is why hook bursts caused multi-GB
RSS spikes and CPU stalls. The on-disk checkpoint also shrinks.

**The checkpoint format changes one way.** v0.2.0 reads checkpoints written
by v0.1.x, but once v0.2.0 writes to a checkpoint, v0.1.x can no longer read
it correctly. Rolling back means restoring the backup from step 2.

## Before you start

| You need | Why |
|---|---|
| Free space for a backup: the size of `wal.canonical.sqlite` + `wal.jsonl` | Rollback. Put it on a different volume if your home disk is tight. |
| Free space for the compacted checkpoint (about 45 % of the old one) | Step 4 writes a new file; the old one is never modified. |
| The server stopped for the duration of steps 2–4 | Compaction refuses to run on a checkpoint that `serve` holds open. |
| `DEEPINFRA_API_KEY` or `OPENAI_API_KEY` in the environment, as before | Unchanged from v0.1.x. |

Measured on the reference substrate (329 k fragments, 7.8 M edges, 14.4 GB
checkpoint, external SSD, a host that was swapping heavily):

| Step | Time | Result |
|---|---|---|
| Backup copy | ~4 min | 15.9 GB copied |
| Compaction (v0.2.1) | ~38 min | 14.4 GB → 6.3 GB, all 8.6 M rows |
| First boot on v0.2.0 | ~2 min | 329,547 fragments restored, no re-embedding |
| Live heap afterwards | — | 2.6 GB (was 12.4 GB), 10.5 M allocations (was 92 M) |

Budget about an hour of downtime for a checkpoint that size on a busy
machine; small substrates take seconds. Use **v0.2.1 or later** for the
compaction: v0.2.0's compactor is correct but several times slower on large
checkpoints.

Hook events that arrive while the server is down are not lost: on restart
the server re-tails each Claude Code transcript from its saved offset.

## Step by step

The commands use two variables; set them first.

```bash
OLD=~/.contextnest                      # where your data lives today
NEW=/path/on/a/roomy/volume/contextnest # where it will live (can equal $OLD)
mkdir -p "$NEW/backup-pre-0.2.0" "$NEW/arena"
```

### 1. Build v0.2.1

```bash
git fetch --tags
git worktree add ../contextnest-v0.2 v0.2.1   # or: git checkout v0.2.1
cd ../contextnest-v0.2
cp ../ContextNest/config.toml .                  # your existing config
cargo build --release
```

Use the **same `config.toml`** as your current server. The checkpoint is
bound to the embedding model configured there; a different model makes the
server discard the canonical state at boot and re-embed everything.

### 2. Stop the server and back up

Stop `contextnest serve` (Ctrl-C, or `make cn-deploy`'s stop step), then:

```bash
sqlite3 "$OLD/wal.canonical.sqlite" "PRAGMA wal_checkpoint(TRUNCATE);"
cp -p "$OLD"/wal.canonical.sqlite* "$OLD/wal.jsonl" "$NEW/backup-pre-0.2.0/"
```

The first command folds SQLite's pending journal into the main file so the
backup and the compaction both see every committed row. Check the copy
before continuing: `ls -l` both locations and compare the sizes.

### 3. Place the WAL

If `$NEW` differs from `$OLD`:

```bash
cp -p "$OLD/wal.jsonl" "$NEW/wal.jsonl"
```

The checkpoint path is always derived from the WAL path
(`wal.jsonl` → `wal.canonical.sqlite` in the same directory), so the two
must sit together.

### 4. Compact the checkpoint (recommended)

```bash
./target/release/contextnest checkpoint compact \
  --from "$OLD/wal.canonical.sqlite" \
  --into "$NEW/wal.canonical.sqlite"
```

It prints a progress line every 250 k rows and, at the end, the row counts
and both file sizes. The source is opened read-only. The command refuses to
run while a server holds the checkpoint, and refuses to overwrite an
existing `--into` file.

Skipping this step is safe: v0.2.0 loads the old JSON rows and rewrites
each fragment in the new format as it is re-persisted. You keep the large
file and the slower boot until then. Without compaction, copy the old
checkpoint to `$NEW` instead (if `$NEW` differs from `$OLD`).

### 5. Start v0.2.0

```bash
CONTEXTNEST_WAL_PATH="$NEW/wal.jsonl" \
CONTEXTNEST_VECTOR_ARENA_DIR="$NEW/arena" \
CONTEXTNEST_CONSOLIDATION_CONCURRENCY=2 \
CONTEXTNEST_CPU_WORKERS=2 \
TOKIO_WORKER_THREADS=4 \
nice -n 10 ./target/release/contextnest serve --bind 127.0.0.1:28080
```

Only `CONTEXTNEST_WAL_PATH` is required (and only when the data moved).
The rest keeps a busy laptop responsive:

| Setting | Effect |
|---|---|
| `CONTEXTNEST_VECTOR_ARENA_DIR` | Keeps the vectors (~4 KB per fragment) in a file-backed mapping. Under memory pressure the OS writes those pages to the file and drops them, instead of compressing and swapping them. The file is rebuilt at every boot and unlinked as soon as it is mapped, so you won't see it in `ls`, but it uses disk space on that volume while the server runs. |
| `CONTEXTNEST_CONSOLIDATION_CONCURRENCY=2` | Halves the background workers (default 4) that embed and link new fragments, so bursts of hook events trigger less work at once. |
| `CONTEXTNEST_CPU_WORKERS=2`, `TOKIO_WORKER_THREADS=4` | Caps the blocking-work and async thread pools. |
| `nice -n 10` | Lets interactive apps win CPU contention. |
| `CONTEXTNEST_MAX_CONNECTIONS_PER_NODE=16` (optional) | Slows graph growth for new fragments; costs some graph-expansion recall. |

With `make`: `make cn-run-existing CN_WAL="$NEW/wal.jsonl"` (after the
build), with the environment variables above exported.

### 6. Verify

```bash
curl -s localhost:28080/api/v1/substrate/health \
  | jq '{fragments, basins: .basins.count, edges: .connections.edges}'
```

- Counts match what the old server reported (the fragment total can be a
  little higher: fragments that were still waiting for consolidation are
  queued again and complete in the background).
- The boot log contains `restored canonical operator checkpoint` with
  `file_backed: true` when the arena directory is set.
- Heap, on macOS: `vmmap --summary $(pgrep -f "contextnest serve")` and read
  **BYTES ALLOCATED** in the MALLOC ZONE table. RSS is not a useful number on
  macOS; it hides compressed and swapped memory.

### 7. Clean up

After the new server has run for a while and a restart has worked:

```bash
rm "$OLD"/wal.canonical.sqlite*        # only if $NEW differs from $OLD
```

If you moved the data, keep a symlink at the old WAL path; the tenant
import command still defaults to it:

```bash
mv "$OLD/wal.jsonl" "$OLD/wal.jsonl.pre-0.2.0" && ln -s "$NEW/wal.jsonl" "$OLD/wal.jsonl"
```

Keep `backup-pre-0.2.0` until you are sure you won't roll back.

## Rollback

1. Stop v0.2.0.
2. In a new directory, put a copy of the **current** `wal.jsonl` next to a
   copy of `backup-pre-0.2.0/wal.canonical.sqlite`.
3. Start the old binary with `CONTEXTNEST_WAL_PATH` pointing at that
   `wal.jsonl`.

The WAL format did not change in v0.2.0, so nothing ingested since the
upgrade is lost: fragments missing from the backup checkpoint are simply
embedded and consolidated again by the old version.

Never point v0.1.x at a checkpoint v0.2.0 has written to. It loads, but the
fragments come back without vectors: retrieval similarity drops to zero and
the graph is empty.

## Troubleshooting

| Symptom | Cause and fix |
|---|---|
| `... is in use (stop contextnest serve first)` | A server still holds the checkpoint lock. Stop it; check with `lsof <path>`. |
| `... already exists; refusing to overwrite` | `--into` points at an existing file. Pick a new path or delete the partial output of an interrupted run. |
| Compaction is slow and the process shows low CPU | It is I/O-bound. Put `--into` on a fast local disk; free memory so the source's pages stay cached. |
| Boot log says fragments=0 and consolidation re-embeds everything | The embedding model or pipeline version differs from the one that wrote the checkpoint. Use the old `config.toml`. |
| `vector arena storage: ...` at boot | `CONTEXTNEST_VECTOR_ARENA_DIR` is not writable or its volume is full or unmounted. Fix the path, or unset it to keep vectors on the heap. |
| `missing ... wal.canonical.sqlite` / empty substrate after moving data | The checkpoint must sit next to `wal.jsonl` and be named `wal.canonical.sqlite`. |
| `sqlite3 -readonly` on the compacted file says `unable to open database file (14)` | A WAL-mode database can't be opened read-only without its `-shm` file. Inspect it with `sqlite3 "file:/path/wal.canonical.sqlite?immutable=1"` while no server is running. |
