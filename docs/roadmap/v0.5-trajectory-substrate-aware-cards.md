# v0.5 — Substrate-aware trajectory cards

**Status:** shipping
**Companion PRs:** #69 (basin-attach-threshold fix prerequisite), #70 (this work)

## Why this exists

The trajectory cards introduced in #66 surfaced flat session statistics
(`records · phases · promotions · risks · per-turn`). They were honest
scalars but ignored every property that makes ContextNest different from
a log viewer — basins, edges, decay, resonance, reconstruction. The
cards looked at one drop of water; the substrate was a pond.

This entry codifies four upgrades that each ground a card surface in a
named substrate primitive from `docs/architecture.md`.

## Upgrades and their primitives

| Card surface | Substrate primitive (see `docs/architecture.md`) | Backend field | Where rendered |
|---|---|---|---|
| **Basin badge** | §3 attractor basin / `AttractorBasinManager::list_basin_snapshots` | `basin_links[]` on `TrajectoryResponse` | inline in card header next to `SessionPill` |
| **Resonance strip** | §5 connection network / `MemoryAttractorManager::list_neighbors` | `resonant_basins[]` | row below the kind-strip, only when non-empty |
| **Promotion clusters** | §3 basin geometry + §1 reinforcement-on-near-duplicates | `promotion_clusters[]` | row below the resonance strip |
| **Heat-weighted sort** | §1 adaptive decay + per-basin write recency | `basin_links[].heat_24h` | `defaultPriorityCompare` + new `heat` sort mode |

## What each upgrade answers

- **Basin badge** — "is this session fresh exploration or the 13th visit
  to the same hot bug?" Hover gives `members_in_session/total_members`
  ratio, last-24h write count, hottest trajectory kind.
- **Resonance strip** — "are there other sessions resonating with this
  one that I'd miss if I only scanned by recency?" `coherence ×
  sessions_touching` surfaces emergent groups the operator wouldn't spot
  by reading individual cards.
- **Promotion clusters** — "are these 9 memory-candidate records noise
  spread across 9 basins, or 3 coherent candidates from 3 sessions in one
  basin (earned promotion)?" Coherent clusters get an accent border.
- **Heat sort** — "which sessions are sitting in the substrate's
  currently-hottest basins?" Bypasses recency to surface load-bearing
  basins.

## Cold-substrate behaviour (graceful degradation)

All four fields default to `[]` when the consolidation worker hasn't
crystallised basins for the session's fragments yet. Cards render the
existing flat statistics and the basin/resonance/promotion rows are
hidden entirely. No skeletons, no loading states — the substrate's
truth is "no basins yet" and the UI reflects that honestly.

## Lock + perf notes

- Backend re-uses the existing `fragment_metadata` read guard pattern
  (§7 architecture lock contract): acquire → synchronous loop → drop.
  Never holds the manager lock across `await`.
- `fragment_to_basin` and `fragment_to_session` reverse indexes are
  built once per request (O(total_fragments)) so the resonance loop
  is O(active_ids × avg_neighbors). For a 50-fragment session with the
  current avg degree of ~131 that's ~6,500 HashMap lookups per request.
- Frontend caps each rendered list at 3 entries (basin_links badge
  shows primary + `+k`, resonance strip and promotion clusters show
  top 3 + `+k`) to keep cards scannable.

## Anti-patterns we resisted

- **Replacing flat counts with basin-stats only.** Counts are honest
  scalars; basins are derived. We keep `records · phases · promotions
  · risks · per-turn` as the ground truth and badge basin context next
  to them.
- **Auto-promoting from resonance.** Resonance surfaces candidates;
  human still approves. Substrate doesn't have intent, only geometry.
- **Rendering resonance for cold sessions.** Gated on `resonant_basins`
  non-empty (which already requires post-consolidation basins).
- **Five surfaces at once.** The original plan had a `reconstruct`-
  powered hover preview as a stretch goal. Deferred — card cognitive
  budget is ~3 signals, and the three substrate strips + basin badge
  already saturate it.

## Future work (not in this PR)

- **Basin drift over time** — render `Δ heat / 7d` so operators can see
  basins cooling / heating. Requires extending the heat calculation to
  carry a windowed series.
- **`reconstruct` hover preview** — substrate already builds answers
  from partial cues; the trajectory card's `goal` field IS a partial
  cue. Connection exists; not wired. Stretch from original plan.
- **Migration / cleanup tracking** — the admin `merge-nearby-basins`
  endpoint (added in #69) lacks a dashboard surface. Operators run it
  via curl today; future PR could add a substrate-page action button.
