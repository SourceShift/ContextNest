# v0.4 Trajectory Prompt Context — Implementation Companion

**Status:** proposal (suggestion-to-implement)
**Owner:** unassigned
**Created:** 2026-05-26
**Parent spec:** [`v0.4-trajectory-prompt-context.md`](v0.4-trajectory-prompt-context.md)

## How to read this doc

The parent v0.4 spec defines **what** to build (architecture, capsule format, API
surface, 5-phase rollout). This companion defines **how** to actually ship it —
with arXiv-grounded mechanisms layered onto the existing ContextNest substrate,
SQL DDL for new tables, Rust module placement matching `src/api/` + `src/services/`
conventions, and acceptance metrics tied to the parent's success criteria.

Three principles drive every decision here:

1. **Reuse, do not parallelize.** The parent spec's "Do Not Build First" list
   is correct and load-bearing. Every component here reuses an existing API
   (`/api/v1/sessions/*`, `/api/v1/tools/retrieve`, `/api/v1/tools/reconstruct`,
   `/api/v1/inbox`) or an existing `MemoryKind`. New persistence only when
   z-insight kinds can't express it.
2. **Earn the LLM call.** Most of the pipeline must work *deterministically*
   from `session_summary` + metadata-filtered retrieve. LLM calls (trajectory
   analyzer, intent classifier) earn their cost only where deterministic
   signal genuinely doesn't suffice.
3. **Augmentation must be inspectable, disableable, and reversible.** Capsule
   injection is a foreign body in the user's prompt. Every directive must be
   evidence-linked, every learning must be promote/demote-able, every session
   must be able to opt out per-prompt without a flag flip.

## Research deltas over the parent spec

The parent doc cites 10 papers. Four additional load-bearing references
materially change the implementation:

| arXiv | Title | Delta over parent spec |
|---|---|---|
| **2604.15877** | Experience Compression Spectrum | Formalises the parent's `Episode → Skill → Rule → PromptDirective` taxonomy as **L0 (raw transcript) → L1 (episodic z-insight) → L2 (skill) → L3 (rule)** with explicit compression ratios (1×, 5–20×, 50–500×, 1000×+). Names the failure mode the parent implicitly avoids: the **"missing diagonal"** — no adaptive cross-level compression. We bake adaptive level selection into the prompt compiler's ranking step. |
| **2603.29194** | Multi-Layered Memory Architectures (MLMF) | Adds the **retention regulariser** `Lret = ‖E(M_s_t) − E(M_s_t−1)‖²` (eq. 9). Without this, semantic memory drifts across sessions — the parent spec mentions "stale memory" but has no concrete drift-control mechanism. Concrete metric to hit: 56.9% six-period retention with 5.1% false-memory rate. |
| **2603.10600** | Trajectory-Informed Memory Generation (TIM, IBM) | Sharpens the parent's "Trajectory Analyzer" §284 into a concrete **3-phase pipeline**: Trajectory Intelligence Extractor → Decision Attribution Analyzer → Contextual Learning Generator. Codifies three tip categories — **strategy / recovery / optimization** — that map onto the parent's `Skill / AntiPattern / PromptDirective` schema. Validated: **+14.3pp SGC on AppWorld held-out, +28.5pp on hard tasks**, optimal retrieval threshold **τ ≥ 0.6**. |
| **2603.13301** | Not All Queries Need Rewriting | The **most important addition**. Empirically shows prompt rewriting **hurts** dense retrieval in some domains. We MUST gate every capsule injection by a retrieval-confidence score and abort enrichment when signal is weak. This is what prevents the augmenter from regressing baseline Claude behavior. |

- **2604.26622 — OCR-Memory** — compress visual evidence in transcripts when token budget tightens.
- **2604.17886 — Latent Preference Modeling** — formalises the parent's `Preference` object §274.

## Mapping the Compression Spectrum onto ContextNest

The parent spec already defines seven `Memory Objects` (§268–278). They are not
arbitrary — they are points on the L0–L3 axis. Naming this explicitly lets us
write a single level-agnostic extractor instead of seven bespoke ones, and lets
us reason about lifecycle uniformly.

| Level | Parent-spec object | Compression | Retrieval cost | Lifecycle TTL |
|---|---|---|---|---|
| **L0** | Raw transcript fragments | 1× | n/a (storage only) | session retention policy |
| **L1** | `Episode`, `TrajectoryStep` | 5–20× | metadata-filtered retrieve | 30d hot, then demoted to L2 candidate |
| **L2** | `Skill`, `AntiPattern`, `Outcome` | 50–500× | hybrid cosine + category | promote on ≥3 confirming traces; demote on ≥2 disconfirming |
| **L3** | `PromptDirective`, project rules, user `Preference` | 1000×+ | always-fetch (small set) | persists with Lret drift control |

**Operational consequence**: the trajectory analyzer is **one function**
parameterised by target level, not three separate analyzers. The level is a
parameter in the analyzer's prompt template, and the same LLM call can emit
multiple levels in one pass with structured-output mode.

## LLM Output Schema — Atomic Discriminated Unions

> **Design correction (2026-05-26).** An earlier draft of this doc used a
> single flat table (`trajectory_learnings`) with a `category` discriminator
> and per-category optional columns (`steps JSONB` nullable when irrelevant,
> `negative_example TEXT` nullable, etc.). That is the **wrong shape for
> LLM-produced data** — the same anti-pattern as `{ type: 'heading', heading?:
> string, text?: string, code?: string }`. The discriminator says "heading"
> but nothing in the schema *forces* `heading` to be present or stops `code`
> from being set anyway. The model can emit invalid combinations; the parser
> will accept them; bad atoms enter the substrate. Fix: replace with a
> **discriminated union** where each variant has its own *fully-required*
> field set, and let the LLM-output toolchain enforce it at decode time.

### How LLMs actually emit structured output today

Every major provider supports **proper discriminated unions** natively. We
target the union shape and let each provider's adapter render it:

| Provider | Mechanism | How discrimination is enforced |
|---|---|---|
| **Anthropic** (Claude 4.x) | tool-use | Either one tool *per variant* (model picks the tool, fields are required for that variant) **or** one tool whose `input_schema` is a JSON-Schema `oneOf` discriminated by `kind`. The model cannot emit a tool call with fields from the wrong variant. |
| **Gemini** (Flash 3 / Pro 3) | `responseJsonSchema` (JSON Schema 2020-12) | Native `oneOf` + `discriminator: { propertyName: 'kind' }`. The decoder rejects outputs that don't match exactly one variant. Note: gemini-3 uses `responseJsonSchema`, NOT the legacy `responseSchema`. |
| **OpenAI** (Responses API) | structured output | `oneOf` with `discriminator`. Validated server-side before decoding. |
| **Vercel AI SDK** (`generateObject`) | Zod schema | `z.discriminatedUnion('kind', [...])` — the SDK compiles to provider-native primitives. |

**Default for ContextNest v0.4 (Rust-native)**: `schemars` crate generating
JSON Schema 2020-12 from `serde` internally-tagged enums, submitted directly
to provider APIs. No Node sidecar; keeps ContextNest a single Rust process.
The discriminator-on-`kind` contract is enforced at three layers: provider
(via the generated schema), `serde_json::from_str::<LearningAtom>` (decode-
time variant matching), and `TryFrom<RawAtom> for LearningAtom` (non-empty
array invariants and similar business rules).

### The atom union

Every output of the trajectory analyzer is an **array of typed atoms**. No
nesting beyond evidence refs. Each atom is independently embeddable,
retrievable, demotable, and renderable.

```ts
// shared/types/prompt_context.ts (TS for clarity — port to Rust serde + JSON Schema)

type Confidence = 'high' | 'medium' | 'low';
type Scope = 'global' | 'user' | 'project' | 'workspace';

type EvidenceRef = {
  fragment_id: string;
  session_id: string;
  turn_idx?: number;            // optional only because some refs aggregate a range
};

type Applicability = {
  scope:        Scope[];        // ≥ 1, never empty
  project_cwd?: string;         // present iff scope includes 'project'
  files?:       string[];       // tightens applicability to a file set
  features?:    string[];
};

type StrategyAtom = {
  kind: 'strategy';
  text: string;                       // 1-sentence directive
  trigger: string;                    // "When task involves X"
  prerequisites: string[];            // [] allowed but field required
  steps: string[];                    // ≥ 1 — required for strategy
  applicability: Applicability;
  evidence: EvidenceRef[];
  confidence: Confidence;
};

type RecoveryAtom = {
  kind: 'recovery';
  text: string;
  trigger: string;
  failure_pattern: string;            // required
  recognition_signals: string[];      // ≥ 1
  recovery_steps: string[];           // ≥ 1
  negative_example: string;           // required — "don't just retry"
  applicability: Applicability;
  evidence: EvidenceRef[];
  confidence: Confidence;
};

type OptimizationAtom = {
  kind: 'optimization';
  text: string;
  trigger: string;
  inefficient_pattern: string;        // required
  efficient_alternative: string;      // required
  steps: string[];                    // ≥ 1
  applicability: Applicability;
  evidence: EvidenceRef[];
  confidence: Confidence;
};

type AntipatternAtom = {
  kind: 'antipattern';
  text: string;
  trigger: string;
  what_to_avoid: string;              // required
  why_it_fails: string;               // required
  alternative: string;                // required — never tell Claude "don't X" without "do Y"
  applicability: Applicability;
  evidence: EvidenceRef[];
  confidence: Confidence;
};

type PreferenceAtom = {
  kind: 'preference';
  text: string;
  scope: Exclude<Scope, 'global'>;    // preferences always have a holder
  preferred: string;                  // required
  rejected: string | null;            // null allowed (some preferences have no opposing example)
  evidence: EvidenceRef[];
  confidence: Confidence;
};

type DecisionAtom = {
  kind: 'decision';
  text: string;                       // one-sentence statement of the decision
  alternatives_considered: string[];  // ≥ 1
  rationale: string;                  // required
  reversibility: 'one-way' | 'two-way';
  applicability: Applicability;
  evidence: EvidenceRef[];
  confidence: Confidence;
};

type EpisodeAtom = {
  kind: 'episode';
  text: string;                       // one-sentence what-happened
  outcome: 'success' | 'failed' | 'blocked' | 'deferred' | 'verified' | 'unverified';
  started_at_idx: number;
  ended_at_idx: number;
  fragment_ids: string[];             // ≥ 1
  session_id: string;
};

type LearningAtom =
  | StrategyAtom
  | RecoveryAtom
  | OptimizationAtom
  | AntipatternAtom
  | PreferenceAtom
  | DecisionAtom;

type Atom = LearningAtom | EpisodeAtom;

// Trajectory analyzer envelope — one of these per analyzed session
type TrajectoryAnalyzerOutput = {
  session_id: string;
  episodes: EpisodeAtom[];            // ≥ 0
  learnings: LearningAtom[];          // ≥ 0
  meta: {
    model: string;                    // e.g. "claude-haiku-4-5"
    elapsed_ms: number;
    parse_retries: number;
  };
};
```

`DecisionAtom` is the 6th learning variant added on review. The parent spec
uses `decision` as a `kind_priority` (§188) and `z-insight-schema.md` lists
`decision` as a `MemoryKind`. Easier to add now than after the schema is in
production.

### Rust mirror

Same shape in Rust (`src/models/prompt_context.rs`):

```rust
#[derive(Serialize, Deserialize, Debug, Clone, JsonSchema)]
#[serde(tag = "kind", rename_all = "snake_case")]
pub enum LearningAtom {
    Strategy {
        text: String,
        trigger: String,
        prerequisites: Vec<String>,
        steps: Vec<String>,                       // validate non-empty in TryFrom
        applicability: Applicability,
        evidence: Vec<EvidenceRef>,
        confidence: Confidence,
    },
    Recovery {
        text: String,
        trigger: String,
        failure_pattern: String,
        recognition_signals: Vec<String>,
        recovery_steps: Vec<String>,
        negative_example: String,
        applicability: Applicability,
        evidence: Vec<EvidenceRef>,
        confidence: Confidence,
    },
    // …Optimization, Antipattern, Preference, Decision
}
```

`serde`'s internally-tagged enum + `#[serde(rename_all = "snake_case")]`
gives us the discriminator-on-`kind` contract. `schemars::JsonSchema`
generates the JSON Schema 2020-12 `oneOf` + discriminator shape for direct
provider submission. Validation of "non-empty arrays" lives in a
`TryFrom<RawAtom>` impl, not in serde — keep serde structurally honest and
push business rules one layer up.

### Why this shape, not the optional-field shape

| Property | Optional-field flat shape (rejected) | Discriminated union (accepted) |
|---|---|---|
| Provider validation | None — JSON Schema can't say "`failure_pattern` required when `kind='recovery'`" without `oneOf` | Native `oneOf` enforces required field set per variant |
| Model failure mode | Emits `kind='recovery'` with `failure_pattern: null` → silently invalid atom enters DB | Schema rejects at decode time; analyzer retries on parse failure |
| Per-variant retrieval ranking | Single embedding, no per-kind tuning | Embed per-kind weight in ranking (`recovery_match * 0.25` when prompt mentions errors) |
| Lifecycle policy | One policy for all categories | Promote/demote thresholds per kind (recovery tips promote faster, preferences slower) |
| Renderer | One big template with N if-branches | One serializer per kind — testable, atomic, deterministic |
| Schema evolution | Adding a new variant requires every consumer to handle new optional fields | Adding a new variant is a new branch in the union; consumers exhaustive-match |

### Capsule output is ALSO atomic

The same principle applies to the *output* of the prompt compiler (what the
hook injects). Earlier draft stored `capsule_markdown TEXT` — a black box. We
replace it with **structured atoms + a deterministic markdown renderer**:

```ts
type CapsuleAtom =
  | { kind: 'inferred_task';     text: string }
  | { kind: 'project_fact';      text: string; evidence: EvidenceRef[] }
  | { kind: 'user_preference';   text: string; evidence: EvidenceRef[] }
  | { kind: 'prior_failure';     pattern: string; recovery: string; evidence: EvidenceRef[] }
  | { kind: 'directive';         text: string; rationale: string; evidence: EvidenceRef[] }
  | { kind: 'file_anchor';       path: string; relevance: string }
  | { kind: 'open_question';     text: string; awaiting_decision_id?: string }
  | { kind: 'stale_warning';     subject: string; last_validated_at: string };

type Capsule = {
  inferred_task: string;
  atoms: CapsuleAtom[];                       // rendered in declaration order
  retrieval_confidence: number;               // 0..1, drives the suppression gate
  source_learning_ids: string[];              // every atom traces back here
  budget_tokens: number;
  tokens_used: number;
};
```

The prompt compiler's job is: **retrieve learning atoms → rank → select →
emit `CapsuleAtom[]`**. No LLM call generates the capsule markdown. A
per-kind `render(atom: CapsuleAtom): string` function deterministically
serializes each atom; the final capsule is `atoms.map(render).join('\n\n')`
with a fixed header.

Four wins:

1. **Inspectable**: every visible line in the capsule has a `kind` and a
   `source_learning_id` — the parent spec's "Why included?" UI surface §57
   becomes trivial.
2. **Disable-per-atom**: the user can drop one `CapsuleAtom` without
   re-rendering the whole capsule.
3. **Cost**: zero LLM tokens for capsule synthesis (the only LLM call at
   prompt-time stays the intent classifier).
4. **Reproducibility**: a stored capsule can be re-rendered byte-identically
   from `atoms[]` — important for Phase 4 outcome attribution.

## SQL DDL for the new tables

Five tables. All FK back to existing `sessions` and `fragments` so evidence
links stay intact. All carry `created_at`, `updated_at`, and `level` (where
applicable) for the Compression Spectrum classification.

**Storage convention**: kind-specific fields live in `payload JSONB`, validated
by the discriminated-union schema at write time (Rust serde round-trip on
insert). Common cross-kind fields stay top-level for indexing and search.
This gives us one analyzer write path, one retrieval path, and per-kind
invariants enforced before the row hits Postgres — without exploding into
per-kind tables (which would force `UNION ALL` on every retrieve).

```sql
-- L1: explicit Episode object aggregating multiple TrajectorySteps from one session
CREATE TABLE episodes (
    id              TEXT PRIMARY KEY,                          -- ep_<uuid>
    session_id      TEXT NOT NULL REFERENCES sessions(id),
    title           TEXT NOT NULL,                             -- "Debugged duplicate session IDs in WAL"
    outcome         TEXT NOT NULL CHECK (outcome IN ('success','failed','blocked','deferred','verified','unverified')),
    started_at_idx  INTEGER NOT NULL,                          -- fragment index range in transcript
    ended_at_idx    INTEGER NOT NULL,
    fragment_ids    TEXT[] NOT NULL,                           -- evidence anchor
    summary         TEXT NOT NULL,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- L2/L3: extracted learning atoms (TIM 2603.10600 §3.1.3, discriminated by `kind`).
-- Per-kind required fields live in `payload`; cross-kind fields are top-level for indexing.
CREATE TABLE trajectory_atoms (
    id                    TEXT PRIMARY KEY,                    -- ta_<uuid>
    kind                  TEXT NOT NULL
                            CHECK (kind IN ('strategy','recovery','optimization','antipattern','preference','decision')),
    level                 SMALLINT NOT NULL CHECK (level IN (2,3)),  -- L2 skill or L3 rule
    -- Cross-kind required fields (always present, indexed for retrieval):
    text                  TEXT NOT NULL,                       -- 1-sentence directive
    trigger_description   TEXT NOT NULL,                       -- "When task involves X"
    applicability         JSONB NOT NULL,                      -- {scope: [...], project_cwd?, files?, features?}
    -- Kind-specific structured payload (validated against the discriminated union at write time):
    payload               JSONB NOT NULL,
    -- Defense-in-depth: payload object MUST contain a `kind` field that matches the column.
    CONSTRAINT trajectory_atoms_kind_payload_match
        CHECK (jsonb_typeof(payload) = 'object' AND payload->>'kind' = kind),
    -- Embedding + lifecycle:
    embedding             VECTOR(1536),                        -- pgvector cosine, hybrid retrieval
    confirming_traces     TEXT[] NOT NULL DEFAULT '{}',        -- episode_ids supporting this atom
    disconfirming_traces  TEXT[] NOT NULL DEFAULT '{}',
    confidence            REAL NOT NULL DEFAULT 0.5 CHECK (confidence BETWEEN 0 AND 1),
    usage_frequency       INTEGER NOT NULL DEFAULT 0,
    last_used_at          TIMESTAMPTZ,
    last_validation_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    status                TEXT NOT NULL DEFAULT 'draft'
                            CHECK (status IN ('draft','active','demoted','retired')),
    promoted_at           TIMESTAMPTZ,
    superseded_by         TEXT REFERENCES trajectory_atoms(id),
    created_at            TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at            TIMESTAMPTZ NOT NULL DEFAULT now()
);
-- App-layer invariant: payload JSON shape MUST match the kind's serde variant.
-- Enforced by `TrajectoryAtomRow::try_into::<LearningAtom>` on every read and
-- by serde round-trip on every write — never by Postgres, because per-kind
-- required fields are a discriminated-union concern.
CREATE INDEX trajectory_atoms_embedding_idx ON trajectory_atoms USING hnsw (embedding vector_cosine_ops);
CREATE INDEX trajectory_atoms_kind_status_idx ON trajectory_atoms (kind, status, level);
CREATE INDEX trajectory_atoms_applicability_gin ON trajectory_atoms USING gin (applicability jsonb_path_ops);

-- Per-kind partial indexes for hot-path retrieval (rank-weight by kind).
CREATE INDEX trajectory_atoms_recovery_active ON trajectory_atoms (last_used_at DESC)
    WHERE kind = 'recovery' AND status = 'active';
CREATE INDEX trajectory_atoms_strategy_active ON trajectory_atoms (last_used_at DESC)
    WHERE kind = 'strategy' AND status = 'active';

-- L3 prompt directives are level=3 rows in this same table — no separate table,
-- lifecycle stays uniform (parent spec §158 design principle preserved).

-- Compiled capsule audit log (the artefact we inject into Claude).
-- Stored as STRUCTURED ATOMS, not a markdown blob — see "Capsule output is ALSO atomic".
-- Markdown is regenerated deterministically from `atoms` via per-kind renderers.
CREATE TABLE prompt_capsules (
    id                    TEXT PRIMARY KEY,                    -- pc_<uuid>
    session_id            TEXT REFERENCES sessions(id),        -- target session, may be NULL pre-session
    user_prompt_hash      TEXT NOT NULL,                       -- SHA256 of original prompt (privacy: not the prompt itself)
    project_cwd           TEXT,
    inferred_task         TEXT NOT NULL,
    atoms                 JSONB NOT NULL,                      -- CapsuleAtom[] (discriminated union, validated)
    rendered_markdown     TEXT NOT NULL,                       -- cached render(atoms); regenerable
    source_atom_ids       TEXT[] NOT NULL,                     -- FKs into trajectory_atoms — every atom traces back
    fragment_ids          TEXT[] NOT NULL,                     -- evidence anchors (flattened across atoms)
    confidence            TEXT NOT NULL CHECK (confidence IN ('high','medium','low')),
    retrieval_score       REAL NOT NULL,                       -- the gate from 2603.13301
    budget_tokens         INTEGER NOT NULL,
    tokens_used           INTEGER NOT NULL,
    aborted_reason        TEXT,                                -- non-null when capsule was suppressed
    created_at            TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX prompt_capsules_session_idx ON prompt_capsules (session_id, created_at DESC);

-- Reflexion-style feedback loop (parent spec Phase 4)
CREATE TABLE capsule_outcomes (
    capsule_id            TEXT PRIMARY KEY REFERENCES prompt_capsules(id),
    completed             BOOLEAN,                             -- did Claude finish the task
    capsule_useful        SMALLINT CHECK (capsule_useful BETWEEN -1 AND 1),  -- -1 hurt, 0 neutral, +1 helped
    directive_ignored     BOOLEAN,
    stale_detected        BOOLEAN,
    user_corrected        BOOLEAN,
    notes                 TEXT,
    recorded_at           TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Per-atom usage telemetry — drives staleness sweep + lifecycle promotion/demotion
CREATE TABLE learning_usage (
    id                    BIGSERIAL PRIMARY KEY,
    atom_id               TEXT NOT NULL REFERENCES trajectory_atoms(id) ON DELETE CASCADE,
    capsule_id            TEXT NOT NULL REFERENCES prompt_capsules(id) ON DELETE CASCADE,
    outcome               SMALLINT,                            -- copied from capsule_outcomes for fast aggregation
    used_at               TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX learning_usage_atom_used_at_idx ON learning_usage (atom_id, used_at DESC);
```

**Migrations**: place under `migrations/` with name
`20260526_v04_prompt_context.sql`. The parent spec §449 explicitly approves new

## Trajectory Analyzer — concrete TIM port

The parent spec §282–296 defines what the analyzer extracts. The TIM paper
gives the **3-phase LLM pipeline** to extract it. **Output shape**:
`TrajectoryAnalyzerOutput` — the discriminated-union envelope defined above
("LLM Output Schema — Atomic Discriminated Unions"). All three phases
contribute to the same envelope; the LLM cannot emit anything outside that
shape.

### Phase A — Trajectory Intelligence Extractor

**Input**: one session's transcript + z-insight records + git diff (when
available via `epic_files[]` + repo lookup) + `session_summary` (already
exists, free).

**Output** (single LLM call, structured JSON):
- Reasoning patterns observed (self-correction, prerequisite verification,
  efficiency awareness — TIM §3.1.1).
- Outcome trajectory (success / failure / recovery / inefficient-success).
- Causal chain markers (which decisions led to which observed outcomes).

**Implementation**: `src/services/prompt_context/trajectory_analyzer/extract.rs`
holds the prompt template + structured-output call. Model: Haiku 4.5 for cost
(this runs nightly across many sessions), with a Sonnet 4.6 retry on parse
failure.

### Phase B — Decision Attribution Analyzer

**Input**: the structured output from Phase A.

**Output**: for each detected outcome, an attribution record naming the
specific decision (with fragment index range) that caused it.

This is the part that bare z-insight does NOT capture today — z-insight
records *that* a learning happened, not *which earlier decision was the
cause*. The attribution analyzer fills this gap and powers high-quality
recovery tips.

### Phase C — Contextual Learning Generator

**Input**: attribution records.

**Output**: structured atoms (`LearningAtom[]` per the discriminated union)
with each variant's required field set populated.

**Granularity decision** (TIM §3.1.2): emit **subtask-level** atoms, not
task-level. TIM §4.2.4 shows subtask-level outperforms task-level on cross-task
transfer. For ContextNest this maps to extracting one atom per
`goal_phase` boundary, not one per session.

### Scheduling

- Trigger: `Stop` hook fires on session completion → enqueue
  `trajectory_analyze` job (background tokio task or sidecar queue).
- Batch budget: ≤ 1 LLM call per session for Phase A+B+C (structured output
  emits all three in one call).
- Failure mode: failed extraction marks the session `trajectory_status='failed'`
  but never blocks ingest. Retry policy: 3 attempts with exponential backoff.

## Intent classifier (Phase 2 — Capsule API)

A cheap LLM call (Haiku 4.5) at capsule-compile time:

**Input**: the user prompt + `project_cwd` + `active_session_id` + (when
available) the immediate session's last 2 z-insights.

**Output** (structured):
```jsonc
{
  "task_type":       "implementation" | "debugging" | "review" | "planning" | "research" | "continuation",
  "risk_level":      "low" | "medium" | "high",
  "time_horizon":    "current_session" | "recent_project" | "long_term_user",
  "entities":        { "files": [...], "features": [...], "errors": [...], "routes": [...] },
  "continuation":    boolean,
  "kind_priorities": ["learning", "decision", "blocker", "feature", ...]   // ordered, drives retrieve
}
```

**Latency budget**: ≤ 300ms p95 (Haiku 4.5 streaming-disabled, structured
output, ~150 input tokens, ~80 output tokens).

**Fallback when LLM unavailable**: deterministic heuristics over prompt
substrings + entity extraction via tree-sitter (file paths, function names).
Capsule still ships; ranking degrades by ~20% on average per parent spec §157
deterministic baseline.

## Ranking formula — Compression-Spectrum-aware

The parent spec §374 defines the ranking formula. We extend it with two
factors from the research:

```text
final_score =
    semantic_similarity      * 0.25
  + task_intent_match        * 0.22
  + project_match            * 0.15
  + recency_decay            * 0.08    // time-aware decay (2510.13590)
  + outcome_quality          * 0.10
  + user_preference_strength * 0.05
  + evidence_quality         * 0.05
  + compression_level_match  * 0.05    // NEW: prefer L3 rules over L2 over L1 for novel tasks
  + retention_stability      * 0.05    // NEW: penalise L3/L2 entries that recently drifted (Lret-derived)
```

The two new terms:

- **`compression_level_match`**: when intent classifier returns
  `task_type=continuation` we want L1 episodes; when `task_type=implementation`
  or `debugging` we want L2 skills + L3 rules. This is the **adaptive level
  selection** the Compression Spectrum (2604.15877 §4 "Problem 1") names as the
  central open problem. We solve a simple version by hard-coded mapping; an
  RL-learned version is a v0.5+ idea.

- **`retention_stability`**: nightly we compute `Lret` per L2/L3 entry as
  `‖embed(text_t) − embed(text_t−1)‖²` after any update. High drift → low
  stability score → ranking penalty. Concretely: if a directive's text was
  rewritten in the last 7 days, downweight it until it's been used once
  successfully without revision.

## Retrieval-confidence gate (the 2603.13301 guardrail)

**Without this, the augmenter can hurt Claude.** The parent spec §504 lists
"Should capsule injection be automatic by default" as open question #1. The
correct answer is: **automatic by default, but gated by retrieval confidence**.

```text
retrieval_confidence =
    weighted_mean(top_3_final_scores)
  - 0.5 * stddev(top_3_final_scores)        // penalty when top hits disagree
  - 0.3 * (1 - evidence_link_coverage)      // penalty when directives have weak provenance
```

Decision rule:
- `retrieval_confidence >= 0.65` → inject capsule normally
- `0.45 <= retrieval_confidence < 0.65` → inject with `<contextnest-low-confidence>` wrapper
- `retrieval_confidence < 0.45` → **suppress** capsule, log `aborted_reason='low_confidence'`,
  ship Claude the bare prompt.

Threshold validated against TIM §4.2 — at τ ≥ 0.6 cosine similarity TIM
achieves +14.3pp SGC, but at τ ≥ 0.5 the improvement narrows to +7.1pp
because low-similarity tips dilute the signal. We pick 0.65 to be more
conservative since capsule injection is more invasive than TIM's tip
retrieval.

## API surface — extends the parent spec

Three endpoints. The first is exactly as the parent spec §223 proposed; the
other two are needed for the Reflexion feedback loop and auditability.

```http
POST /api/v1/prompt-context/compile          # synchronous capsule build
POST /api/v1/prompt-context/feedback         # log capsule outcome (Reflexion)
GET  /api/v1/prompt-context/capsules/:id     # audit + inspect a capsule
```

### `POST /api/v1/prompt-context/compile`

Exactly as parent spec §227 — request/response shape unchanged. Implementation
note: **stream nothing**, return synchronously with p95 ≤ 800ms total
(intent classify 300ms + parallel retrieve 200ms + rank+compile 100ms +
serialise 100ms + margin 100ms).

### `POST /api/v1/prompt-context/feedback`

```jsonc
{
  "capsule_id":           "pc_...",
  "completed":            true,
  "capsule_useful":       1,           // -1 hurt, 0 neutral, +1 helped
  "directive_ignored":    false,
  "stale_detected":       false,
  "user_corrected":       false,
  "notes":                "Tip about k8s secrets was directly applied."
}
```

Updates `capsule_outcomes` + denormalises into `learning_usage.outcome` for
fast aggregation. Drives the lifecycle: 3 capsules where `capsule_useful=+1`
for a given `atom_id` → eligible for promotion L2→L3; 2 capsules with
`capsule_useful=-1` in 14 days → eligible for demotion.

### `GET /api/v1/prompt-context/capsules/:id`

Returns the stored `prompt_capsules` row + linked `trajectory_atoms`
records + outcome if recorded. Used by the parent spec's "Prompt Context
Preview" UI surface §52.

### Phase 4 · Feedback Loop (parent §472)

**Effort**: 5–7 eng-days

- Land `POST /api/v1/prompt-context/feedback`.
- Auto-infer feedback when possible: session completion → `completed=true`;
  Claude response cites or follows a directive → `capsule_useful=+1`;
  Claude response contradicts a directive → `capsule_useful=-1`.
- Manual feedback: dashboard button + Claude Code slash command
  `/contextnest-feedback <-1|0|+1> [notes]`.
- Lifecycle worker (nightly cron):
  - Compute `Lret` per atom, write `retention_stability` field.
  - Promote L2 → L3 on ≥ 3 positive uses + ≥ 0.9 confidence.
  - Demote L2/L3 on ≥ 2 disconfirming uses in 14d.
  - Retire on 60d zero usage.
- **Acceptance**: ≥ 5 promotions/week, ≥ 0 false promotions surviving > 14d.

## Risks + mitigations

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Capsule injection actively hurts Claude responses (2603.13301). | Medium-High | High | Confidence gate (§retrieval-confidence-gate); 4-week A/B with user-pref measurement; revert hook if `capsule_useful≤0` mean rate > 30%. |
| Trajectory analyzer rate-limits or breaks under backfill volume. | Medium | Medium | Haiku for cost; batch in 10-session chunks; exponential backoff on rate-limit. |
| Semantic memory drifts (no retention regulariser baseline). | Medium | Medium | Nightly Lret compute + `retention_stability` ranking penalty (MLMF 2603.29194 eq. 9). |
| L3 rules over-generalise from ≤3 sessions, producing false invariants. | High if unguarded | High | Promotion threshold ≥ 3 confirming + ≥ 0.9 confidence + user confirmation for first L3 rule per project; auto-demote on first disconfirming use within 14d. |
| Capsule leaks secrets/PII into a future prompt. | Low (self-hosted) | High | Reuse existing privacy filter (`E-privacy-filter.md` epic); never include command output verbatim in capsule, only fragment references; pre-injection redaction pass. |
| Hook adds noticeable latency at `UserPromptSubmit`. | Medium | Medium | p95 budget 800ms hard cap; hook fails open on timeout; intent classifier on Haiku not Sonnet. |
| ContextNest substrate retrieval (`/api/v1/tools/retrieve`) becomes the bottleneck. | Low (already optimised) | Medium | Cache embedding of user prompt for the session; parallel retrieve across kind filters; profile during Phase 2 dev. |
| Stale capsules from before this work persist after migration. | Low | Low | One-time backfill script + status='draft' on all newly extracted atoms until manual review or 3 positive uses. |

## Anti-patterns to actively avoid

Lifted from the parent spec's "Do Not Build First" §113 and validated by
arXiv:2604.15877 §3.4 ("specialisation alone is insufficient"):

- **Do not** add a separate vector store for `trajectory_atoms` — pgvector
  on the new table reuses the existing infra.
- **Do not** re-parse Claude transcripts — Phase 1 analyzer reads from
  existing `cc_hooks.rs` ingested z-insight rows + the existing
  `session_summary` API.
- **Do not** treat L1 episodes and L2 atoms as two separate systems — one
  table with `level` discriminator, one analyzer parameterised by level.
- **Do not** inject capsules without confidence gating — 2603.13301 shows
  ungated rewriting actively hurts some queries.
- **Do not** rely on LLM summarisation for the hot path — the parent spec
  §116 is right that deterministic `session_summary` already does this
  cheaply.
- **Do not** ship without a manual feedback mechanism — Reflexion-style
  closed-loop is what prevents memory rot (parent §472 Phase 4).
- **Do not** use optional-field-with-discriminator for LLM output schemas
  — model can emit invalid combinations the parser silently accepts. Use
  a discriminated union with per-variant required-field sets. See
  "LLM Output Schema — Atomic Discriminated Unions".
