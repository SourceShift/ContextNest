# v0.4 z-insight Trajectory Signals

**Status:** proposal
**Created:** 2026-05-26
**Source transcript:** `~/.claude/projects/-Volumes-docker-ssd-Migration-Development-ContextNest/e899a4cc-ede2-4c2c-b315-6cbaf16b34eb.jsonl`

## TL;DR

The current Claude Code ingest is already useful: a dry-run over recent
ContextNest transcripts extracted 2,797 memories with 0 extraction failures.
The selected session `e899a4cc-ede2-4c2c-b315-6cbaf16b34eb` was then ingested
into the live substrate at `http://localhost:28080`, producing 86 stored
memories with 0 failures. It produced good `goal_phase`, `learning`, `todo`,
`user_action`, `feature`, and `files_touched` records.

The missing data is not more prose. The missing data is **turn-level
provenance**:

- what the assistant read before deciding;
- what commands/tests verified the claim;
- what failed and how it recovered;
- which decisions were made vs merely proposed;
- what should be injected into the next Claude prompt;
- what confidence, scope, and staleness each memory has.

Add these as optional `z-insight` fields first, then teach the extractor to
promote them into typed `MemoryKind`s.

Post-ingest caveat: the CLI reported `INGEST COMPLETE` with 86 success / 0
fail, but a follow-up `/api/v1/sessions/.../summary` probe could not be repeated
because the local server was no longer accepting connections on port 28080.
This is exactly the kind of nuance that should live in `verification[]`.

Selected-session examples showed the current schema can preserve:

- session goal changes, such as Makefile alignment, `cc-` prefix refactor, and
  embedder context-limit fix;
- shipped features through `delivered_features[]`, including files, refs,
  `how_to_test`, and symbol definitions;
- user-blocking actions, such as GitHub merge clicks or runtime restart checks;
- useful facts, such as live WAL size, clippy scope, and permission-system
  behaviour.

The same transcript also showed what is underrepresented:

- `Read`, `Grep`, `Glob`, and documentation discovery are not captured as a
  durable read-context signal;
- verification is embedded inside `top_jobs[]` or `how_to_test`, not normalized
  into pass/fail command records;
- failures and recovery attempts are mixed into prose, so future prompt
  compilation cannot reliably say "when this error appears, do this";
- decisions made by the user are not separated cleanly from decisions awaiting
  the user;
- evidence anchors are mostly free-form `refs`, not structured enough to
  retrieve exact files, commands, transcript turns, or PRs.

## Recommended z-insight additions

All fields are optional and backward-compatible. Emitters can add them now;
old consumers ignore them.

### 1. `read_context[]`

What the assistant inspected before acting.

```jsonc
{
  "path": "docs/z-insight-schema.md",
  "kind": "doc|source|test|config|transcript|external",
  "reason": "Understand current z-insight schema before proposing extensions",
  "salient": "delivered_features[] is stored as MemoryKind::Feature",
  "refs": ["docs/z-insight-schema.md:70"]
}
```

Why: prompt compilation needs to know which docs were trusted. `files_touched`
answers "what changed"; `read_context` answers "what grounded the decision."

### 2. `verification[]`

What was run, what passed, and what remains unverified.

```jsonc
{
  "kind": "shell|curl|manual|test|dry_run",
  "command": "cargo run --quiet -- ingest claude-code --session-id e899a4cc --dry-run",
  "status": "passed|failed|blocked|not_run",
  "summary": "Extracted memories without extractor failures",
  "counts": {"memories": 2797, "failures": 0}
}
```

Why: future Claude prompts should distinguish "implemented and tested" from
"planned" and from "not run because the server was down."

### 3. `evidence_refs[]`

Structured pointers that support later audit and prompt grounding.

```jsonc
{
  "kind": "file|command|pr|commit|url|transcript_turn|log",
  "ref": "src/ingest/claude_code/extractor.rs:214",
  "claim": "Extractor walks assistant turns and parses z-insight blocks"
}
```

Why: current `refs` are useful but feature-scoped and free-form. Prompt
context needs evidence-linked directives so injected guidance can be inspected.

### 4. `decisions[]`

Decisions already made, not questions awaiting the user.

```jsonc
{
  "decision": "Use bare Claude Code UUIDs as canonical session IDs",
  "made_by": "user|assistant|team",
  "alternatives": ["keep cc- prefix", "API-boundary strip", "source-tag schema"],
  "rationale": "Existing Claude Code UUIDs are globally unique enough for current scope",
  "reversibility": "one_way|two_way",
  "scope": "project"
}
```

Why: the existing `decision` field is tied to `awaiting_decision`. We also need
settled decisions so the next prompt can preserve architectural intent.

### 5. `failures[]`

Errors, failed commands, permission denials, and recovery actions.

```jsonc
{
  "symptom": "gh pr merge denied by permission policy",
  "root_cause": "default-branch merge requires human approval",
  "recovery": "Ask user to click merge or add an explicit permission rule",
  "status": "open|resolved|accepted",
  "refs": ["PR #58", "PR #60"]
}
```

Why: long-term trajectory analysis depends on failure-to-recovery patterns, not
only successful accomplishments.

### 6. `prompt_directives[]`

Small, scoped instructions that a future prompt compiler may inject.

```jsonc
{
  "trigger": "When modifying ContextNest ingest or session IDs",
  "directive": "Check WAL migration and live ~/.contextnest/wal.jsonl compatibility before changing ID shape",
  "scope": "project",
  "confidence": "high",
  "evidence": ["e899a4cc-ede2-4c2c-b315-6cbaf16b34eb"]
}
```

Why: this is the direct bridge from transcript memory to better Claude prompts.
It should be compact, triggerable, and evidence-linked.

### 7. `assumptions[]`

Assumptions that shaped the work and may go stale.

```jsonc
{
  "assumption": "A live-ingest result should be rechecked through the session API after the substrate is confirmed running",
  "basis": "The ingest CLI reported success, but a follow-up summary curl later failed because port 28080 was no longer accepting connections",
  "valid_until": "next runtime check",
  "risk_if_wrong": "A future prompt may treat CLI success as the same thing as API-level retrieval verification"
}
```

Why: stale assumptions are one of the easiest ways for long-lived memory to
mislead the next agent.

### 8. `artifacts[]`

Docs, plans, reports, generated files, and external artifacts that are not
features.

```jsonc
{
  "kind": "doc|report|plan|research_note|todo|patch",
  "path": "docs/roadmap/v0.4-z-insight-trajectory-signals.md",
  "purpose": "Store transcript-derived z-insight extension plan",
  "status": "created|updated"
}
```

Why: many valuable outputs are planning artifacts, not shipped product
features. Treating all of them as `delivered_features` pollutes feature search.

### 9. `memory_candidates[]`

Explicit promotion candidates for ContextNest's long-term memory layers.

```jsonc
{
  "kind": "preference|rule|gotcha|workflow|antipattern",
  "text": "For ContextNest ingest work, run dry-run ingest before changing extractor schema",
  "scope": "project",
  "confidence": "medium",
  "promote_after": "second_confirmation"
}
```

Why: not every `fact` should become a rule. This gives the substrate a
promotion queue instead of relying on repeated prose.

### 10. `risk_flags[]`

Security, privacy, data-loss, and migration hazards.

```jsonc
{
  "risk": "Live WAL migration can rewrite user data",
  "severity": "high",
  "mitigation": "Require backup before startup migrator runs",
  "scope": "project"
}
```

Why: prompt enrichment should raise high-consequence constraints earlier than
ordinary facts.

## Extractor changes

Add these `MemoryKind`s:

| New kind | Source field | Default importance | Notes |
|---|---|---:|---|
| `read_context` | `read_context[]` | 0.65 | Include path/kind/reason metadata; do not confuse with `files_touched`. |
| `verification` | `verification[]` | 0.85 if failed/blocked, 0.75 if passed | Store command/status/counts. Used by "what was actually tested?" queries. |
| `evidence_ref` | `evidence_refs[]` | 0.60 | Mostly metadata; can also be attached to related records. |
| `decision_made` | `decisions[]` | 0.90 | Higher than `learning`; prevents re-litigating settled choices. |
| `failure` | `failures[]` | 0.85 | Connect to recovery and future anti-pattern atoms. |
| `prompt_directive` | `prompt_directives[]` | 0.95 | Candidate L3 memory for prompt compiler. Requires scope + trigger. |
| `assumption` | `assumptions[]` | 0.55 | Must carry staleness/validity metadata. |
| `artifact` | `artifacts[]` | 0.70 | Planning/report outputs distinct from features. |
| `memory_candidate` | `memory_candidates[]` | 0.80 | Promotion queue; not automatically a durable rule. |
| `risk_flag` | `risk_flags[]` | 0.90 | High-consequence constraints for future prompts. |

Keep the existing permissive parser. If a field is malformed, skip that item
and attach a parse-warning memory only in debug mode; do not fail the whole
session ingest.

## Prompt compiler implications

When the user sends a new Claude prompt, compile context in this order:

1. Fetch active `prompt_directive` and `risk_flag` records for the project and
   matching file/topic scope.
2. Fetch recent `decision_made`, `failure`, and `verification` records for the
   same scope.
3. Fetch `read_context` and `artifact` records only when they match the current
   task's docs/files.
4. Demote `assumption` records unless they are recent or explicitly validated.
5. Use existing `learning`, `feature`, `todo`, and `goal_phase` as supporting
   context, not as primary directives.

The injected capsule should be short:

```text
ContextNest memory capsule:
- Directive: When changing Claude ingest schema, run dry-run ingest first.
- Decision: Bare Claude Code UUIDs are canonical; do not restore cc- prefix.
- Risk: WAL migration touches live user data; require backup before rewrite.
- Live ingest state: Session e899a4cc stored 86 memories / 0 failures into http://localhost:28080.
```

## Rollout plan

### Phase 1 - Schema-only emission

- Update `docs/z-insight-schema.md` with the optional fields.
- Update local assistant final-message template to emit `verification`,
  `artifacts`, `assumptions`, and `risk_flags` immediately.
- Do not change storage yet.

Acceptance: old ingester still extracts existing fields; new fields appear in
raw transcript blocks.

### Phase 2 - Extractor support

- Extend `MemoryKind`.
- Parse each new field into one record per item.
- Add extractor unit tests for valid and malformed arrays.
- Add dry-run summary counts for the new kinds.

Acceptance: targeted `--session-id e899a4cc --dry-run` shows new records without
regressing current counts.

### Phase 3 - Retrieval surfaces

- Add metadata filters for `kind=verification`, `kind=decision_made`,
  `kind=prompt_directive`, and `kind=risk_flag`.
- Extend `/api/v1/sessions/:id/summary` to include verification state and
  decisions made.
- Keep `/api/v1/inbox` limited to user actions and awaiting decisions.

Acceptance: "what was tested in this session?" and "what decisions should a
future prompt preserve?" are answerable without transcript grep.

### Phase 4 - Prompt-context integration

- Feed `prompt_directive`, `decision_made`, `risk_flag`, and recent failed
  `verification` into the v0.4 prompt compiler.
- Require evidence refs for any directive that is injected.
- Add feedback logging so bad directives can be demoted.

Acceptance: prompt capsules improve continuation quality without injecting
unverified or stale assumptions.

## Open questions

1. Should `verification[]` allow command output snippets, or only summaries and
   counts to avoid leaking large logs?
2. Should `read_context[]` be emitted by the assistant manually, inferred from
   `Read`/`Grep` tool calls, or both?
3. Should `prompt_directives[]` be authored directly by the assistant or only
   generated by a background trajectory analyzer after the session ends?
4. Should `memory_candidates[]` be promoted by repetition, explicit user
   approval, or a confidence threshold?
